# DSR-013：低延迟读路径——冻结快照 + 写屏障替代读写单飞

## 上下文

初版所有 API 方法（含读）进入同一个单飞队列串行执行，一次列表渲染伴随多遍全库扫描；技能页打开与刷新感知明显。R-17 要求变更操作串行、不产生交错状态，但读操作并不需要与写操作互斥到「排队等扫描」的程度。

## 真实方向与评价

- 方向 A：保持读写共用单飞队列。一致性语义最简单（任何读都读到最新），但读延迟与写延迟互相拖累，设置页这种高频读场景体验差。
- 方向 B：读路径走进程内 bundle 缓存（root 键 + 约 800ms TTL + 单飞冷扫的冻结快照），写操作进行中的读先等写屏障结算，每个写方法收尾重算并预热缓存；网络慢方法（check/search/repo-skills）独立队列。读在缓存热时零扫描零存储读；一致性代价是读可能返回数百毫秒内的快照，由「写后预热 + 短 TTL + 配置目录变更键失配」收口，对管理界面足够。
- 方向 C：引入文件系统 watcher 驱动失效。 freshest，但 watcher 可靠性跨平台有坑，且设置页场景不需要秒级外变更感知；复杂度无证据支持。

## 最终决定

采用方向 B（2026-08 下旬落地，commit `02d67ab`「低延迟重构」；本记录为追溯补记）：

1. 三路调度：读方法（overview/warm/health/project-skills/backups）不排队；文件写方法 FIFO 串行（写写互斥，R-17 保留）；网络慢方法独立队列。
2. 三级缓存：bundle 快照（库扫描 + 工作区投影 + 健康代际）、SKILL.md meta 按 stat 签名复用、`dirHash` 短 TTL（5s）——破坏性路径（update 的本地修改判定）强制 fresh 重算，写操作统一清空哈希缓存。
3. 聚合只读视图 `overview`：单请求下发库列表（含意图叠加、挂载目标推导、上游检查缓存）+ 健康 + 工作区投影。
4. Host 启动后延迟 1s 后台预热（配置了目录时），首次打开设置页秒出。

## 直接后果

- 新增 `lib/cache.js`；`lib/api.js` 重写为三路调度 + 缓存门面；`index.js` 增加启动预热定时器。
- R-17 的「所有变更操作串行」语义收窄为「写操作 FIFO 串行 + 读走冻结快照」，需求与验收语义不变。
- `check` 结果缓存（DSR-008）叠加在投影之上：`library` 视图的上游徽章读 `check_cache` 表，页面打开零网络请求。

## 重访条件

- 快照延迟（约 800ms 窗口）在实测中产生可感知的一致性投诉。
- 库规模增长到单飞冷扫本身成为瓶颈（数百 skill 以上）时，重访增量扫描或 watcher（方向 C）。
