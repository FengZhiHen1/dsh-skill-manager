# DSR-008：技能行操作 ⋯ 菜单、候选复选批量入库、全局刷新状态直显

## 上下文

设计稿评审（2026-08-19，对照 DSH 原生设置界面）发现三处交互未定型或与实现不一致：

1. 技能行操作：实现侧每行内联 检查/更新/禁用/删除 按钮与换组 select；设计稿仅有 ⋯ 占位，无菜单界面，也无换组入口。
2. 多 skill 仓库候选（03 帧）：原为单选 ✓ + 每行各一个「入库」按钮，选中态与行内动作关系模糊。
3. 「检查更新状态」与「立即更新」并列为行内动作；上游状态（已是最新/可更新）需要逐行手动触发才可见，而逐行检查意味着每 skill 一次串行网络请求（`remoteHead`），列表扫描本身（`scanLibrary`）是纯本地操作。

## 真实方向与评价

- 方向 A：行操作保持内联按钮 + 行内换组 select（实现现状）。操作可见性最好，但每行 4-5 个控件，列表噪音大；与原生设置页的克制风格不符。
- 方向 B：行操作收纳进 ⋯ 菜单（立即更新/禁用/移动到分组 ▸/删除），行内只保留状态徽章与 ⋯。行视觉干净，换组通过子菜单完成；代价是操作多一次点击，且需要新增菜单组件。
- 候选入库 A：单选 + 行内入库（现状）。一次只能入库一个，多 skill 仓库（如 anthropics/skills）需反复探测-入库。
- 候选入库 B：复选 + 底部统一「入库所选」。批量场景一次完成；与探测先行语义（DSR-007）自洽。代价：需要多选状态与批量入库循环。
- 状态可见性 A：保留行内「检查更新状态」动作（逐行按需网络探测）。无全局状态视图，用户无法一眼看出哪些 skill 可更新。
- 状态可见性 B：去掉行内检查，由工具栏全局「↻ 刷新」触发批量检查，行徽章直接显示状态（本地态每次扫描即得；上游态取自最近一次检查并标注检查时间）。一眼可见全库状态；代价：需要检查结果缓存与并行探测，否则串行探测慢且打满 GitHub 匿名限额。

## 最终决定

采用 B / B / B 组合（2026-08-19 用户逐项确认）：

1. 行操作以 ⋯ 菜单为准：立即更新 / 禁用 / 移动到分组 ▸（子菜单列分组，当前组打勾）/ 删除（红色）。行内不再放动作按钮。
2. 候选行为复选框 + 底部「入库所选」统一按钮，附已选计数。
3. 去掉「检查更新状态」入口；状态直显：徽章只表达状态（已同步/可更新/本地有修改），全局刷新触发批量检查，界面标注「上游状态检查于 HH:MM」。

## 直接后果

- 设计稿：`skill-manager-management.op` 新增 08 帧（⋯ 菜单与移动分组）；03 帧改为复选 + 入库所选；01/07/08 行徽章统一为 20px 灰底小胶囊（正常态灰字、可更新深色字、本地有修改琥珀），行内动作按钮全部移除。
- 实现待修正项：
  - `client.js` 行内 检查/更新/禁用/删除 按钮与换组 select 改为 ⋯ 菜单 + 分组子菜单。
  - 搜索/探测候选 UI 改复选 + 批量入库（`add` 需支持或循环调用）。
  - `check` 的串行 `remoteHead` 循环并行化；检查结果缓存（含检查时间戳）并随 `library` 返回，刷新按钮触发重新检查。
  - 修正前，插件运行时.md 与本文档描述为权威语义，实现现状视为未达标。
- 徽章配色约定：状态徽章用中性灰底（原生 pending pill 样式），仅警告态用琥珀；彩色徽章只保留在 05 帧同步矩阵（健康矩阵语义）。

## 重访条件

- 菜单操作被证明过于隐蔽（用户找不到更新/禁用入口）时，重访行内常驻「更新」按钮。
- GitHub 匿名限额或探测延迟在实测中不可接受时，重访检查策略（仅检查可见行、降低频率或手动单行检查回退）。
