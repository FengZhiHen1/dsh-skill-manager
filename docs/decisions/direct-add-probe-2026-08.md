# DSR-007：直接添加入口语义以「探测仓库」为准

## 上下文

02 帧设计稿（`plugins/dsh-skill-manager/design/skill-manager-management.op`）中「从 GitHub 仓库添加」区的按钮文案是「探测仓库」，而实现侧 `client.js` 的 `DirectAdd` 按钮文案是「添加」，且其多候选分支报错"仓库含多个 skill……请先用搜索或指定目录"。二者哪个符合功能原始定义需要裁定。原始定义见 R-08（"输入 owner/repo 直接入库；……多 skill 仓库先返回候选列表，选择后入库"）与 plugin-runtime.md § 搜索视图（"直接添加框：先调 `repo-skills`，多候选时展示选择列表，单候选直接进入确认"）；设计稿 03 帧「多 Skill 仓库候选」即探测结果的候选选择界面。

## 真实方向与评价

- 方向 A：以「添加」为准。设计稿按钮改文案，实现保持现状（多候选报错、引导改用搜索）。按钮标注最终目的，但多候选分支与 R-08、plugin-runtime.md「多候选时展示选择列表」直接冲突，03 帧的候选列表界面在直接添加路径下成为不可达状态。
- 方向 B：以「探测仓库」为准。设计稿不变；实现修正 `DirectAdd`：点击即探测（`repo-skills`），多候选展示候选选择列表（复用 `SearchView` 已有的候选 UI 模式），单候选进入入库。按钮标注第一步真实动作，语义诚实，与 R-08、plugin-runtime.md、03 帧完全自洽。代价：需要改动实现与测试。
- 方向 C：文案与流程解耦——按钮统一叫「入库/添加」，但流程按探测两步走（多候选展示列表）。流程正确，但文案把两步封装成一步，用户在多候选弹出的候选列表前缺少预期；相对于 B 没有实质收益。

## 最终决定

采用方向 B。依据：2026-08-19 用户确认「探测仓库」更贴近该功能的原始含义；R-08 与 plugin-runtime.md 定义的就是"探测先行、候选再选"的两步流程，03 帧是其多候选状态的既有设计。

## 直接后果

- 设计稿 02 帧「探测仓库」按钮保持不变，不视为与实现的文案冲突。
- 实现待修正项：`client.js` `DirectAdd` 的多候选分支由"报错并引导改用搜索"改为"展示候选选择列表"（对齐 `SearchView` 的候选交互与 03 帧），按钮文案统一为「探测仓库」；修正需同步更新 `test/` 中相关断言。
- 修正完成前，plugin-runtime.md § 搜索视图的描述（多候选展示选择列表）继续作为权威语义，`DirectAdd` 现状视为未达标实现而非设计变更。

## 重访条件

- 若 `repo-skills` 探测与 `add` 入库合并为单一 RPC（探测不再是用户可感知的独立步骤），重访方向 C 的一步式文案。
- 若 skills.sh 注册表覆盖到足够全面、直接添加路径主要服务私有/内部仓库且均为单候选，可重访是否简化多候选分支。
