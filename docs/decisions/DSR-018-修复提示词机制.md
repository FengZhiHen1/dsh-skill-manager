# DSR-018：修复提示词机制——Host 供 facts，Client 统一模板组装

> 状态：已确认（2026-09-01，design-spec-workshop 新基线重设计，用户裁定），代码实施待执行；与 DSR-014/015/016/017 合并为一次实施批次（登记于 `../TODO.md`）。

## 上下文

新需求基线把「失败修复提示词」升为一等机制：R-17 要求预期外失败或自动执行边界内的歧义情形，除清晰提示外提供一键复制的修复提示词（含完整上下文与推荐方案）交本地 Agent 处理；AC-15 给出验收；C-04 把歧义现场（目标被占用、指向库外的链接等）的出口统一指向该机制。需要定落地形态：提示词在哪里组装、覆盖哪些失败面。

失败呈现面有三类，事实分布不对称：

1. RPC 操作失败：Host 拥有全部事实（绝对路径、目标根、配置快照、错误分类）。
2. settings 校验拒绝（如非绝对路径、非法组名）：Host 不产出业务错误，上下文在 Client 手里（草稿值、当前值、校验消息）。
3. 行状态「挂载失败」：走查结果由 Host 经 `overview` 下发，用户从行徽章进入。

## 真实方向与评价

- 方向 A：Host 预渲染完整提示词文本，Client 只复制。Client 零逻辑；但 settings 拒绝面 Host 不参与，仍需 Client 侧第二套组装，两个组装点并存；文案迭代需重启 Host。
- 方向 B：Host 在错误对象上附加结构化 `repair` facts，Client 用统一模板组装最终文本。三类呈现面共用一个组件；文案归 Client（刷新即生效）；Host 只供事实，平面职责干净。代价是 Client 增加一个模板组件。
- 方向 C：纯 Client 组装。Client 事实不足（不知道绝对路径与目标根），需要 Host 额外下发同样的事实——等于把方向 B 的事实传输做了一半却放弃其统一性。

## 最终决定

采用方向 B（2026-09-01 用户确认）：

1. 传输中立 Result 的错误对象在 `error.details.repair` 携带结构化 facts：

```json
{
  "operation": "update",
  "summary": "覆盖更新被拒绝：检测到本地修改",
  "facts": [{ "label": "配置目录", "value": "E:\\Project\\Skills" }],
  "recommendation": ["确认本地修改已另行保存", "确认后勾选复选框重试"]
}
```

2. `repair` 由 core 按错误码的元数据表生成（`summary`/`recommendation` 按 code 取模板，抛出点携带动态 facts：操作名、相关路径、配置快照）；未分类异常（`internal`）同样携带通用模板，保证任何失败都有复制入口。
3. Client 提供统一「复制修复提示词」组件：把 facts 模板化为完整提示词（插件与操作背景、错误码与消息、上下文清单、推荐处理方案、只读红线提醒），一键复制；RPC 错误、settings 校验拒绝（Client 本地上下文走同一组件）、行状态「挂载失败」徽章点击展开三处呈现面共用。
4. 错误码表收缩：随本地导入、空目录接管、工作区归一删除，`import` 相关码、`bad-claim`、`workspace-migration-conflict` 等一并删除；剩余码全部登记 repair 元数据。

## 重访条件

- 修复提示词需要多语言或用户自定义模板时，重访模板归属。
- 本地 Agent 侧出现结构化接入口（如直接接收 facts JSON）时，重访纯文本模板形态。
