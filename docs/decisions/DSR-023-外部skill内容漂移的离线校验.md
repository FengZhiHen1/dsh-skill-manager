# DSR-023：外部 skill 内容漂移的离线校验

> 状态：**草案，未开工**。判据、成本与落点均已取到实据（见「背景与证据」「成本实测」），但**第 4 条（触发时机与 TTL 取值）与第 5 条（页面呈现范围）需用户确认**后才进入实现。编号现查 `decisions/` 目录确认（接 DSR-022）。

## 背景与证据

- 直接触发：2026-09-09 为实测场建基线闸时，采集脚本的单次全库哈希立刻报出——试验 HOME 的 `yao-meta-skill` 现场哈希 `599a4422…` 与 `skills` 记录基线 `860a23a3…` 不符。该记录入库于 09-06，**这三天里没有任何界面提示过它被改过**；同期生产 HOME 采集为零漂移（说明不是普遍故障，是**没人看得见**）。
- **判据已存在，不是新造**：`src/core/inbound/upstream.js:88` 就是 `(await hashDir(hash, dest)) !== entry.content_hash`，三态（`null` = 无基线不可判），配套还有 `baseline_missing`（`:104`）。
- 缺的是**触发面**：这段判据只在 `check` 里跑，而 `check` 属 `NET_METHODS`（`service.js:27`）——必须先打上游拿 head sha。⇒ **不联网或没点「检查」，就没有漂移信号**，尽管这纯粹是个本地计算。
- Client 半区同样已就绪：`manage.jsx:48` 的「本地有修改」旗标、`:147` 的分支都挂在 check 结果上 ⇒ 本 DSR 不需要新 UI 元件，需要的是把判据结果**在没有网络时也喂进去**。
- 附带缺陷：同一判据在 `upstream.js` 写了两遍（`:88` 观测路径、`:154` update 前破坏性预检，后者刻意 `fresh=true` 不信缓存）。加第三个调用点前必须先收成单源。

## 成本实测（2026-09-09，生产现场，只读探针）

| 范围 | 规模 | 全量哈希 |
| --- | --- | --- |
| 生产**插件库根**（github 条目） | 1 目录 / 725 文件 / 12.3 MB | **231 ms** |
| 生产**用户根**（全部条目，含 29 条 self） | 22 目录 / 25 873 文件 / **3.4 GB** | **14 691 ms** |
| 用户根前 8 条 | 24 054 文件 / 3.4 GB | 8 124 ms |

结论先给：**校验范围只能是插件库根的 github 条目**。纳入 self 条目单次就要 14.7 秒、读 3.4 GB，任何路径都塞不下；且 self 目录是用户自己维护的，改内容不构成异常。

## 决策（草案）

1. **范围** = `origin:"github"` 且 `content_hash` 非空的条目。self/local 与无基线条目一律不入漂移计数（后者继续走既有 `baseline_missing` 三态，报「无基线不可判」）。
2. **判据单源**：把重复两处的「现场哈希 vs 登记基线」收成一个函数（落 `model/library.js`，与 `dirHash` 同处；形如 `contentDrift({ hash, dir, baseline })`），观测路径可吃缓存、破坏性预检强制 `fresh`——**两种调用语义保留，实现只一份**。禁止出现第二套哈希比较。
3. **离线**：漂移校验**绝不触网**，也不受 `check` 失败影响。它与 `check` 共享判据但触发与失败面分开：`check` 回答「上游有没有新版」，漂移回答「我本地的这份还是当初那个吗」。
4. **触发时机（待你定）**：
   - 甲 每趟 `overview` 全算 —— 单条目 231 ms，线性放大（30 条 github ≈ 7 s）违背 DSR-013 低延迟读路径 ⇒ 否。
   - 乙 **进程内 TTL 懒校验（推荐）** —— 挂进 `createSharedCache()` 同层，与 bundle 缓存一起冷扫时算；TTL 取值待你定（我建议 30 分钟起步，页面首开最多慢一次，之后零成本）。
   - 丙 只在写操作/对账后算 —— 漂移恰恰发生在没人动插件的时候，单独不够 ⇒ 不做。
   按极简优先：**只做乙**，不预先做组合方案；实测若发现 TTL 内看不到必要的新漂移再谈。
5. **报告落点**（零 UI 改动优先）：
   - 汇总进 `lib.warnings` 一条 —— 与 DSR-022 的 `describeUnmanagedLinks` 同形态，Client 侧 `manage.jsx:113` 已全量渲染 warnings，**不改一行前端就能可见**。措辞草案：「N 个外部 skill 的内容与入库基线不符（可能被手工修改或损坏）；运行「检查」可逐条定位」。
   - 逐条定位继续用已有的「本地有修改」旗标，不新建字段。
   - **不放** `health.issues`：该面 `issue` 虽为自由串，但 Client 只对 `"orphan-link"` 精确匹配消费（`manage.jsx:125`），放了也不显示，只是白扩接口面。
   - 徽章链（`manage.jsx:37-41`）本 DSR **不动**：「已改动」该排在「可更新」前还是后是视觉判断，留待页面走查时定。
6. **不得污染 `check_cache`**：判定依据只有 `skills.content_hash` + 现场哈希（`目录配置与状态存储.md:165` 的铁律：任何判据、门禁与不变式都不得读 `check_cache` 作依据）。第 4 条乙的结果缓存**只作节流**，放进程内 shared 缓存、随进程消失，不落 `check_cache` 表——否则「上次检查时间」显示会开始说谎。
7. **姿态 = 只报不改**（与 DSR-022「宁可残留」同向）：不自动重算基线（`upstream.js:85` 既有注释已确立「不把当前内容静默写成新基线」）、不自动恢复、不阻止挂载。恢复是用户动作，出口已有 `restore`/`update`。

## 直接后果

- 断网、从未点过「检查」的实例也会知道外部内容被改过——这是本 DSR 的全部目的。
- 首次读路径多一次 github 库全哈希（实测 231 ms/条目），TTL 内零成本。
- 与 `tools/skill-manager-baseline.mjs` 的漂移报告**同源同判据但用途不同**：脚本是实测场「开工前后取证」（含 self 条目、离线、人工跑），插件是日常可见（只 github、自动）。脚本继续保留，不合并。

## 被否方案

- **另存基线文件/往 `managed_links` 记内容哈希** ⇒ 语义污染（那张表只记归属，不记内容），且制造第二个不可重算事实源。
- **纳入 self 条目** ⇒ 14.7 s / 3.4 GB，且用户改自己的 skill 目录本属正常，报告只会变噪音。
- **一键「接受当前内容为新基线」** ⇒ 把损坏固化成正常；若真有需求须做成显式用户动作并另立 DSR。
- **新开 `verify` 端点供页面按需调** ⇒ 违背「只实现被请求的功能」与 DSR-013；TTL 懒校验已覆盖同一需求。

## 验证计划

1. 断网单测：注入不可用的网络层 → 漂移照样报，`check` 失败不得影响判定。
2. **判据单源静态闸**：仿 `AUDIT_OPS` 双向门禁的做法，静态扫 `src/core` 内「与 `content_hash` 比较」的表达式，只允许出现在第 2 条的单源函数体内（闸本身的局限同 DSR-022：依赖字面写法）。
3. 范围闸：造一条 self 条目改内容 → 漂移计数与 warnings 均为 0；造一条 github 改内容 → 计数 1。
4. TTL 节流：连续两次 `overview` 只触发一次全哈希（以 `dirHash` 调用计数断言）；配置变更/写操作后 TTL 失效并重算。
5. 三态：`content_hash:null` 条目 → 报 `baseline_missing`，不并进漂移。
6. 成本回归：fixture 造 N 条 github 条目，冷扫耗时线性、单条目数量级不劣于现场实测。
7. 真机（test 实例，用户起）：入库一个**一次性演示仓库**（AGENTS 红线：不得用生产在用 github 源）→ 手改其库内文件 → 开页面确认 warnings 出现该条汇总。**此条与演示仓库绑定**，合成库里的 `demo-*` 是 self 条目，验不到。

## 重访条件

- github 条目数量级增长使冷扫不可接受 ⇒ 增量哈希（按 `mtime`+size 预筛再哈希）。
- DSH 提供官方 skill 完整性校验通道 ⇒ 本 DSR 退役，只保留判据适配。
- 出现「漂移后想恢复原内容」的真实诉求 ⇒ 另立 DSR 讨论 `restore` 入口与基线来源（备份 vs zipball 重下）。
